# Design idea: one glossary, used everywhere

Status: idea (2026-11-25). Open questions below. Not the design until
promoted.

## The problem

The same thing is called by different words in different places, and
today's design ideas add new terms. There are two glossaries already,
and they disagree:

- `doc/design/README.md`, "Glossary" (15 terms): a scale is an
  "ordered set of degree names"; a lane is "one row inside a group, one
  per note (pitch) or stroke type". Both are out of date once
  [what a note shows](2026-11-25-note-label.md) and [collapsed
  rows](2026-11-25-collapsed-rows.md) are promoted.
- `doc/design/01-notation.md`, "Concepts" (11 terms), overlapping the
  first with different wording.

The manual has none, and nothing ties the code's names (procedures,
record fields, JSON keys, error messages) to either.

Examples of the drift:

| Thing | Words in use |
|---|---|
| `dong` in a scale | degree, degree name, note name, pitch |
| `o` (its `:display`) | display form, display name, label |
| a row inside a group | row, lane (`lanes` in the JSON, "row labels" in options) |
| what is written in a note | note name, text, label |

## Agreed (2026-11-25)

- **One glossary** defines each term once, and documentation and code
  use those terms consistently.
- **One file**, `doc/design/glossary.md`. It replaces the design
  README's "Glossary" and 01's "Concepts", which point to it.
- **No glossary in the manual.** The manual uses the glossary's
  user-facing terms, but doesn't list them.
- **"Row" everywhere.** The JSON's `lanes` and `lane` become `rows` and
  `row` in contract version 4 (see the iteration README); "lane label"
  becomes "row label" in the docs. The feature called the "annotation
  lane" until now is the **annotation row**.
- **The code follows the glossary.** Procedure, record field and JSON
  names use its terms; they are renamed when a milestone next touches
  the code, not in one sweep.
